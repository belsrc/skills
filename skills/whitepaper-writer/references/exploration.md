# Exploration and Subagent Dispatch

How to run the reconnaissance pass without burning main-thread context on it, read OpenSpec specs correctly (with or without a capability index), and divide work across subagents so coverage scales with repo size instead of being capped at a fixed handful of buckets.

Dispatch happens in two phases. Phase 1 is a single reconnaissance subagent, dispatched alone and waited on. Phase 2 is the fixed baseline plus all dynamic subsystem subagents, dispatched together once Phase 1's plan is in hand. Phase 2 can't start before Phase 1 finishes, since the dynamic subagent list is Phase 1's output — but Phase 1 itself is not a swarm, it's one subagent.

---

## Phase 1: The Reconnaissance Subagent

Recon touches a lot of raw surface area: directory listings, every living doc's existence, every OpenSpec capability, every top-level package's shape. None of that raw material needs to sit in the orchestrating (main) context once a plan has been drawn from it — so recon runs in its own subagent, and the main thread only ever holds the compact plan that comes back, not the discovery trail that produced it. This is the same reasoning as not letting exploratory tool output accumulate in a driver context generally: isolate the expensive, disposable exploration in a subagent whose context gets thrown away, and keep only the distilled result.

**Explore**:

1. **Documentation directories**: `docs/`, `documentation/`, and any nested equivalents
2. **Living docs** at the scope root: which of `ARCHITECTURE.md`, `CONSTRAINTS.md`, `JARGON.md`, `EPISTEMIC-MAP.md`, `README.md` exist. Existence only here — the actual deep read happens in the docs-synthesis fixed-baseline subagent in Phase 2, not in recon. Reading them twice at full depth would be exactly the kind of duplicated cost this two-phase split exists to avoid.
3. **`openspec/specs/`**: this directory MUST be checked unconditionally, independent of whether an `INDEX.md` is present inside it. See "Reading OpenSpec Specs" below — this is the one recon step that does involve some real reading, because reconstructing a capability map without a pre-built index requires it.
4. **Source structure**: top-level packages/modules within scope, their entry points (from `package.json`/`Cargo.toml`/`pyproject.toml` or equivalent), and rough size (file count is a fine proxy)
5. **Test directories**: where they live and roughly what they cover

**Return** — a dispatch plan, not raw findings:

1. Which living docs and doc directories exist (paths only; the docs-synthesis subagent reads content)
2. The OpenSpec capability picture: either the parsed `INDEX.md` table, or the reconstructed equivalent when there's no index — capability name, one-line purpose, known relations
3. A proposed subsystem list for Phase 2's dynamic subagents: directory boundary, rough size, and which OpenSpec capabilities (if any) are assigned to it — including cross-cutting capabilities with no directory of their own
4. Test directory locations

If the returned plan is missing something a later subagent clearly needs (a subsystem the recon pass under-scoped, a capability that didn't get assigned anywhere), you MAY adjust it before Phase 2 dispatch — the plan is a working draft you finalize, not a contract to follow blindly if it's visibly incomplete.

## Reading OpenSpec Specs

This is recon's job, in Phase 1, not something the main thread or a later subagent redoes.

`openspec/specs/<capability>/spec.md` files are worth reading whenever they exist, full stop. An `INDEX.md` summarizing them is generated by internal tooling that wraps OpenSpec and will only be present in repos using that tooling — its absence is not a signal to skip `openspec/specs/`, only a signal recon will need to build the summary itself instead of reading a pre-built one.

### With an `INDEX.md`

A capability index looks like this (real example, trimmed):

```markdown
| Capability | Purpose | Related | Last Touched By |
| ---------- | ------- | ------- | --------------- |
| agent-directory-detection | The Agent Directory Detection capability provides automatic discovery of global agent skill directories across multiple AI coding assistant platforms. | cli-core-platform, interactive-prompts, skill-symlink-support | init-interactive-agent-selection |
| ci-mode-filtering | Provide deterministic, high-confidence filtering for CI/CD pipelines by retaining only findings where structural analysis is sufficient. | | ci-flag-deterministic-filtering |
```

Three columns, three different trust levels:

- **`Capability`**: a slug, usually (not always) corresponding to `openspec/specs/<capability>/spec.md`. Treat this as a checklist item — every capability in the index should be accounted for *somewhere* in the whitepaper, even if only as a paragraph inside a larger subsystem section.
- **`Purpose`**: OpenSpec's own summary of the capability. This is a fast-start draft, not a citation — recon can carry it forward into the plan as-is, but flag it as unverified, since actual verification against code happens later in Phase 2, not during recon.
- **`Related`**: a same-level dependency/adjacency hint, not a clustering key. In a mature repo this graph is dense — `cli-orchestration`-style hub capabilities relate to a dozen others, and naive connected-components clustering on this column tends to produce one giant supercluster that isn't useful for drawing subagent boundaries. Use it instead to tell a subagent which neighboring capabilities it may need to reference while writing its section, and to catch a capability that has no matching directory in the repo structure — those are cross-cutting concerns (see below).
- **`Last Touched By`**: provenance — which OpenSpec change last edited the *spec file*, not the code. It tells you nothing about whether the code has since moved past the spec. You MUST NOT cite this as evidence a spec is current.

Reading the index itself is cheap — it's already a compact table. Recon can parse it directly with little added cost.

### Without an `INDEX.md`

If `openspec/specs/` exists but has no `INDEX.md`, you MUST NOT skip it — but keep the read light, since this is the one place recon's cost can balloon if done carelessly:

1. List the subdirectories of `openspec/specs/`. Each is typically a capability slug, the same shape as the `Capability` column above, just without the table.
2. For each, skim rather than fully ingest — the purpose statement is almost always the opening paragraph of `spec.md`, and capability-name mentions elsewhere in the file are usually enough to infer relations without reading the whole document. Full depth reading of spec content is the docs-synthesis subagent's job in Phase 2, working from richer context; recon just needs enough to place each capability on the map.
3. Reconstruct what an index would have given you: capability name, one-line purpose, inferred relations.
4. Cross-reference against the directory scan exactly as in the INDEX.md case — obvious directory match joins that subsystem's scope, no match means cross-cutting.

This is more work than reading a pre-built table, but recon's job stays the same either way: place every capability on the map, verify nothing yet.

### No `openspec/` Directory At All

Nothing here to check — skip this part of recon and rely on the docs/living-docs inventory plus the directory scan.

**Cross-referencing against the directory scan** (either case above): diff the capability list against the source-structure inventory. Capabilities with an obvious directory match (e.g. `tree-sitter-integration` → a `parser/` or `tree-sitter/` directory) become part of that subsystem's Phase 2 scope. Capabilities with no directory match at all (`ci-mode-filtering`, `verification-terminology`, `boolean-naming-detection`) are cross-cutting: logic threaded through existing files rather than a place of their own. You MUST assign each of these to whichever subsystem is most likely to encounter it in code (a rule-engine subsystem picks up `boolean-naming-detection`; the CLI-orchestration subsystem picks up `ci-mode-filtering`) rather than leaving it stranded with no subagent to cover it.

## Phase 2: Fixed Baseline Subagents

These MUST always be spawned, regardless of what recon found. This is what guarantees coverage doesn't silently depend on an agent's judgment call about whether something matters.

### 1. Docs, Living-Docs, and Specs Synthesis

**Explore**: the docs/living-docs/specs content recon's plan pointed at — this subagent does the actual deep reading recon deliberately deferred, now guided by recon's map instead of starting from nothing.

**Return**: a synthesized picture of what the system is documented to do, tagged clearly as *documented*, not yet *verified*. This subagent's output feeds directly into Step 4 (reconciliation) — it is deliberately the one subagent whose findings are provisional until cross-checked against what the other subagents find in actual code.

### 2. Core Architecture and Entry Points

**Explore**: `package.json`/`Cargo.toml`/`pyproject.toml` (whichever applies) for entry points and exports, the top-level composition of the system (what calls what, at a glance), the overall data/control flow.

**Return**: the shape of the architecture diagram (this subagent's findings usually become the mermaid flowchart), a description of the system's top-level composition, and identification of what the "core model" actually is — including whether it has genuine mathematical/algebraic structure or is better described as a taxonomy (see `references/whitepaper-template.md`).

### 3. Types and Data Models

**Explore**: the type system — exported types, discriminated unions, generic constraints, config schemas, validation logic.

**Return**: the type architecture with real signatures (not paraphrased), generic constraints and why they exist, and any type-safety patterns worth calling out as design decisions rather than incidental structure.

### 4. Tests-as-Behavior

**Explore**: test files — not for coverage metrics, but for what they reveal about actual behavior, edge cases the team cared enough about to test, and any place tests contradict what docs or specs claim.

**Return**: behavior confirmed by tests (highest-confidence claims in the whole whitepaper, since tests can't drift from behavior the way prose does), and a flagged list of anywhere tests contradict documented intent.

## Phase 2: Dynamic Subsystem Subagents

One per subsystem identified in recon's plan — a directory/package/module with enough surface area (multiple files, a distinct concern) to warrant its own exploration. A single utility file is not a subsystem; you MUST fold it into whichever fixed-baseline or sibling subsystem subagent is the natural home for it rather than spawning a subagent with almost nothing to explore.

**Explore**: the subsystem's source, its own tests if distinct from the general test sweep, any subsystem-local docs, and the cross-cutting OpenSpec capabilities recon assigned to it.

**Return**: same contract as the fixed baseline — verified purpose, file:line citations, representative snippets, conflicts found, candidate mathematical structure.

## Subagent Task Template

Use this shape for every Phase 2 dispatch, fixed or dynamic (Phase 1's recon subagent has its own shape above, since its return contract is a plan rather than verified content):

```
Explore <scope> within <repo/package root>.

Sources to check:
- <specific files/directories from recon's plan relevant to this subagent>

Return:
1. A verified purpose statement — what this subsystem actually does, checked against
   code, not copied from any doc
2. File:line citations for every non-trivial claim
3. 2-4 representative code/config snippets worth quoting in the whitepaper, with source paths
4. Any conflicts found between docs/specs and actual code behavior
5. Whether this subsystem has genuine mathematical/algebraic structure worth
   formalizing, or is better described as a taxonomy/decision tree
```

Item 2 is for you, the orchestrator, to verify and reconcile with — it is not a preview of the finished whitepaper's prose. The file:line references a subagent returns MUST NOT be transcribed wholesale into the document; see `references/code-truth-and-conflicts.md`'s Citation Discipline section for what citation style actually belongs in the finished writing. Similarly, item 4's conflicts feed Step 4's reconciliation and Step 8's separate user report — they do not become their own section in the whitepaper.

You MUST dispatch the fixed baseline and all dynamic subsystem subagents together, in the same turn, once recon's plan is in hand — you MUST NOT wait for one of them to finish before starting the next.
